1. Project Overview
Build a SaaS platform used by multiple organizations to plan projects, assign work, collaborate, automate workflows, track delivery, and analyze team performance. Each organization must see only its own users, projects, tasks, files, and reports.

3. Learning Outcomes
Translate a real business problem into a maintainable software architecture and a set of verifiable requirements.
Build a typed, responsive React/Next.js frontend and secure Node.js/Express REST APIs.

Deploy and operate a working application, explain design trade-offs, and respond to production-style incidents.

5. Architecture and Engineering Expectations
Use a modular architecture. The Next.js application is the user interface; Express is the primary business API; FastAPI is a separate service for the domain-specific processing/analytics responsibility described in the assessments. PostgreSQL is the system of record. Redis may be used for caching and asynchronous jobs.
Define service boundaries and document which service owns each data entity. Avoid duplicating authoritative business data across services.
Validate all untrusted input on the server. Never rely on frontend-only checks for security or business rules.
Use database transactions for operations that must succeed or fail together. Document concurrency-control decisions.
Use consistent API response/error formats, pagination, filtering, request IDs, and versioning.
Keep secrets out of source control. Commit only a safe .env.example with placeholder values.
Make background jobs retry-safe and idempotent. Record failed jobs and provide a controlled recovery path.
Include health/readiness endpoints, structured logs, meaningful metrics, and graceful shutdown behavior.
Document trade-offs. A technically valid alternative is acceptable when the learner explains why it is appropriate.

Two users update the same task at nearly the same time. The platform must prevent silent overwrites, preserve a complete activity history, and avoid duplicate notifications when background jobs retry.
The evaluator may introduce a controlled failure or edge case. The learner must reproduce the issue, inspect logs and data, identify the root cause, implement a fix, add a regression test, and explain how recurrence will be prevented.
8. Cross-Cutting Non-Functional Requirements
Security: Enforce authorization server-side; validate input; protect secrets; use HTTPS in deployed environments; apply least privilege; avoid exposing sensitive records in logs.
Reliability: Handle timeouts, retries, duplicate events, process restarts, and dependency outages. Do not retry non-idempotent actions blindly.
Performance: Paginate large collections, index measured query patterns, avoid N+1 access, and provide evidence for significant optimization claims.
Accessibility and usability: Use semantic controls, keyboard navigation, visible validation, loading/empty/error states, and responsive layouts.
Maintainability: Use clear modules, typed contracts, linting/formatting, meaningful names, migration discipline, and documented configuration.
Observability: Use structured logs, correlation/request IDs, health checks, actionable error reporting, and basic metrics.
Data integrity: Use constraints, transactions, explicit state transitions, audit history for important changes, and backup/restore validation.

This is an educational engineering assessment, not a certification of legal, financial, medical, or regulatory compliance. Use synthetic data and sandbox integrations.
